NAGHME 2.0 — PHASE 01 / STEP 1
DATABASE & DOMAIN ARCHITECTURE AUDIT

گزارش ممیزی و برنامهٔ معماری
تاریخ بررسی: 2026-09-03

----------------------------------------------------------------------
1. EXECUTIVE SUMMARY
----------------------------------------------------------------------

نغمه در وضعیت فعلی یک آرشیو موسیقی شخصیِ کاربردی و نسبتاً پایدار است که
بر پایهٔ Expo React Native، TypeScript، Expo Router، SQLite محلی و معماری
Android-first / offline-first ساخته شده است.

مدل فعلی برای استفادهٔ شخصی و چند هزار قطعه مناسب است، اما هنوز مدل کامل
یک آرشیو حرفه‌ای موسیقی نیست.

مهم‌ترین محدودیت‌ها:

1. Tracks هم‌زمان نقش قطعه، ضبط، نسخه و بخشی از اثر موسیقایی را دارد.
2. هر Track فقط یک artistId دارد و اعتبارهای چندگانه مثل خواننده،
   آهنگساز، ترانه‌سرا و تنظیم‌کننده پشتیبانی نمی‌شود.
3. Work، Version، Role، Credit، Source، Artwork و Collection هنوز
   entity واقعی نیستند.
4. رابطهٔ Album و Artist در دیتابیس وجود ندارد و Graph بخشی از آن را با
   دادهٔ hard-code شده می‌سازد.
5. ترتیب رسمی قطعات آلبوم ذخیره نمی‌شود و بعضی queryها به rowid تکیه دارند.
6. سیستم migration واقعی وجود ندارد؛ فقط چند ستون به‌صورت دستی و ناقص
   اضافه می‌شوند.
7. تعداد شنیدن در دو مسیر متفاوت محاسبه می‌شود:
   - از ListeningHistory
   - از PersonalRelationships.listeningCount
8. Backup/Restore داده‌های رسانه‌ای را منتقل نمی‌کند و Restore برخلاف متن
   رابط کاربری، merge انجام می‌دهد، نه overwrite کامل.
9. Journal ساختار خوبی دارد و free-form است، اما فقط در صفحهٔ Track
   قابل مشاهده است.
10. AI و Gemini اختیاری هستند و پیشنهاد محلی وجود دارد، اما گفت‌وگوی AI
    کاملاً offline نیست و ذخیرهٔ دائمی ندارد.

پیشنهاد اصلی:

- ابتدا زیرساخت migration، index و consistency اصلاح شود.
- سپس بدون حذف یا تغییر شناسه‌های فعلی، مدل Work / Version / Credit / Role
  به‌صورت تدریجی اضافه شود.
- Tracks به‌عنوان نام legacy حفظ شود و در مفهوم جدید نقش Recording را
  داشته باشد.
- Album و Collection کاملاً جدا باقی بمانند.
- Source، Artwork و روابط Artist به Artist در مرحلهٔ بعدی ساخته شوند.

2. CURRENT DATABASE MODEL
----------------------------------------------------------------------

تعریف اصلی دیتابیس در این فایل قرار دارد:

artifacts/naghme/src/db/database.ts

2.1 جدول Artists

فیلدها:

- id: TEXT، Primary Key، اجباری
- name: TEXT، اجباری
- type: TEXT، nullable
- biography: TEXT، nullable
- genres: TEXT، nullable
- image: TEXT، nullable
- profileImage: TEXT، nullable
- galleryImages: TEXT، nullable

نکات:

- galleryImages به‌صورت یک رشته ذخیره می‌شود و در UI به‌صورت JSON parse
  می‌شود.
- image و profileImage تا حدی نقش مشابه دارند.
- نقش‌های موسیقایی به‌صورت آزاد داخل type قرار می‌گیرند.
- هیچ رابطهٔ artist-to-artist در دیتابیس وجود ندارد.

2.2 جدول Albums

فیلدها:

- id: TEXT، Primary Key، اجباری
- title: TEXT، اجباری
- releaseYear: INTEGER، nullable
- coverImage: TEXT، nullable

محدودیت‌های فعلی:

- releaseDate ندارد.
- عنوان جایگزین ندارد.
- description، genre، label و notes ندارد.
- timestamp ندارد.
- artistId ندارد.
- ترتیب رسمی قطعات ندارد.
- جدول واسط Album/Track وجود ندارد.
- آلبوم فقط با Tracks.albumId به Track متصل می‌شود.

2.3 جدول Tracks

فیلدها:

- id: TEXT، Primary Key، اجباری
- title: TEXT، اجباری
- duration: INTEGER، nullable
- artistId: TEXT، nullable، FK به Artists
- albumId: TEXT، nullable، FK به Albums
- audioUri: TEXT، nullable
- coverImage: TEXT، nullable
- lyrics: TEXT، nullable
- sheetMusicUri: TEXT، nullable
- versionName: TEXT، nullable

روابط:

- artistId -> Artists.id
- albumId -> Albums.id
- هر دو با ON DELETE SET NULL

محدودیت‌های فعلی:

- یک Track فقط یک Artist دارد.
- Work واقعی وجود ندارد.
- Version واقعی وجود ندارد.
- versionName فقط متن آزاد است.
- سال، زبان، genre، description و notes وجود ندارد.
- Track، Recording و نسخهٔ اجرا از هم تفکیک نشده‌اند.
- cover مربوط به Track و cover مربوط به Album جدا هستند، اما abstraction
  مشترک ندارند.

2.4 جدول PersonalRelationships

فیلدها:

- trackId: TEXT، Primary Key و FK
- rating: REAL، nullable
- favorite: INTEGER، اجباری، پیش‌فرض 0
- emotionalTags: TEXT، nullable
- personalNote: TEXT، nullable
- listeningCount: INTEGER، اجباری، پیش‌فرض 0

رابطه:

- هر Track حداکثر یک PersonalRelationship دارد.
- حذف Track باعث حذف رابطهٔ شخصی می‌شود.

قابلیت‌های موجود:

- امتیازدهی 1 تا 5
- favorite
- یادداشت شخصی
- emotional tags در مدل وجود دارد، اما UI فعلی کنترل کاملی برای آن ندارد.
- listening count در جدول ذخیره می‌شود.

مشکل مهم:

listeningCount با رکوردهای واقعی ListeningHistory همیشه هماهنگ نیست.

2.5 جدول JournalEntries

فیلدها:

- id: TEXT، Primary Key
- trackId: TEXT، اجباری، FK
- note: TEXT، اجباری
- mood: TEXT، اجباری
- createdAt: DATETIME، اجباری

قابلیت‌ها:

- چند entry برای یک Track پشتیبانی می‌شود.
- entry قابل ایجاد، ویرایش و حذف است.
- Journal آزاد است و به پرسش‌نامهٔ rigid تبدیل نشده است.
- با حذف Track، entryها cascade delete می‌شوند.

محدودیت‌ها:

- فقط به Track متصل است.
- updatedAt ندارد.
- author/user ندارد؛ برای معماری single-user فعلی قابل قبول است.
- صفحهٔ مستقل Journal وجود ندارد.

2.6 جدول ListeningHistory

فیلدها:

- id: TEXT، Primary Key
- trackId: TEXT، اجباری، FK
- listenedAt: DATETIME، اجباری

این جدول در واقع Listening Event فعلی است، اما نام legacy آن
ListeningHistory است.

در حال حاضر ندارد:

- مدت گوش‌دادن
- completion percentage
- context
- source
- device
- session
- نوع رویداد
- زمان پایان پخش

2.7 Indexها و محدودیت‌ها

به‌جز indexهای ضمنی Primary Key، index ثانویه‌ای تعریف نشده است.

Indexهای فعلی وجود ندارند برای:

- Tracks.artistId
- Tracks.albumId
- Tracks.title
- JournalEntries.trackId
- JournalEntries.createdAt
- ListeningHistory.trackId
- ListeningHistory.listenedAt
- ستون‌های جست‌وجو

برای تعداد کمی داده مشکلی ایجاد نمی‌کند، اما در آرشیو چند هزار قطعه باعث
کندشدن search، history، recommendation و graph خواهد شد.

2.8 Migration فعلی

در database.ts فقط چند migration دستی وجود دارد:

- Artists:
  - profileImage
  - galleryImages
- Albums:
  - coverImage
- Tracks:
  - artistId
  - lyrics
  - sheetMusicUri
  - versionName

مشکلات:

- جدول migration وجود ندارد.
- PRAGMA user_version استفاده نشده است.
- ترتیب نسخه‌ها ثبت نمی‌شود.
- migrationها transaction ندارند.
- خطاهای ALTER TABLE عملاً نادیده گرفته می‌شوند.
- اگر یک جدول قدیمی ستون‌های پایهٔ دیگری را نداشته باشد، اصلاح نمی‌شود.
- تغییر constraintها یا foreign keyهای قدیمی پشتیبانی نمی‌شود.
- CREATE TABLE IF NOT EXISTS ساختار قدیمی را اصلاح نمی‌کند.

3. CURRENT DOMAIN MODEL
----------------------------------------------------------------------

بیشتر مدل‌های TypeScript در این فایل قرار دارند:

artifacts/naghme/src/db/queries.ts

3.1 مدل‌های اصلی

مدل‌های موجود:

- ArtistRecord
- AlbumRecord
- TrackRecord
- PersonalRelationshipRecord
- JournalEntryRecord
- ListeningHistoryRecord
- VersionTrackRecord
- HomeTrackRecord
- RecommendationTrack
- MusicGraphRow
- ChatArchiveContext

مدل‌ها تقریباً مستقیماً از شکل rowهای SQLite کپی شده‌اند.

3.2 مشکل coupling

queries.ts هم‌زمان سه نقش دارد:

1. تعریف domain type
2. repository/query layer
3. تبدیل و mapping داده‌ها

این باعث شده domain objectها به شکل فعلی SQL وابسته باشند.

نمونه‌های coupling:

- TrackRecord تقریباً همان row جدول Tracks است.
- MusicGraphRow یک projection مستقیم از SQL است.
- RecommendationTrack یک joined projection است.
- VersionTrackRecord entity نسخه نیست و فقط Trackهای هم‌نام را نمایش می‌دهد.
- UI در چند بخش خودش mapping دستی از Track انجام می‌دهد.

3.3 مدل جداگانهٔ Store

در src/store/useAppStore.ts یک مدل کم‌حجم‌تر برای Track وجود دارد که فقط
بخش‌هایی مانند id، title، duration، albumId، audioUri و coverImage را دارد.

این مدل موارد زیر را ندارد:

- artistId
- lyrics
- sheetMusicUri
- versionName

در UI فعلی نیز مدل اصلی پخش از audio manager می‌آید، نه از Store.

3.4 وضعیت پخش صدا

در src/audio/audioManager.ts وضعیت پخش به‌صورت singleton ماژولی نگهداری
می‌شود.

شامل:

- track id
- audio URI
- title
- artist name
- album/cover metadata
- isLoaded
- isPlaying
- buffering
- error
- position
- duration
- repeat mode
- sleep timer

این معماری برای یک پخش‌کنندهٔ single-user مناسب است، ولی queue واقعی یا
context playback هنوز وجود ندارد.

3.5 مدل Graph

Graph با یک مدل مستقل canonical کار نمی‌کند. اطلاعات از چند بخش ترکیب
می‌شوند:

- Artist
- Album
- Track
- MusicGraphRow
- لینک‌های hard-coded seed

بنابراین Graph در حال حاضر یک tree projection است، نه graph domain واقعی.

3.6 مدل AI

ChatArchiveContext شامل این داده‌هاست:

- تاریخچهٔ اخیر شنیدن
- Journal entryها
- Trackهای پرتکرار
- Artistهای پرتکرار

این مدل برای context فعلی مناسب است، اما:

- conversation ذخیره نمی‌شود.
- AI context entity مستقل نیست.
- مدل memory یا preference برای AI وجود ندارد.
- AI context مستقیماً از queryهای تجمیعی تولید می‌شود.

4. CURRENT RELATIONSHIPS
----------------------------------------------------------------------

4.1 Artist -> Track

از طریق Tracks.artistId.

- یک Artist به چند Track
- هر Track حداکثر یک Artist
- nullable

این رابطه در مدل فعلی primary artist محسوب می‌شود، اما نقش دقیق آن
ذخیره نشده است.

4.2 Album -> Track

از طریق Tracks.albumId.

- یک Album به چند Track
- هر Track حداکثر به یک Album
- nullable

4.3 Track -> PersonalRelationship

از طریق PersonalRelationships.trackId.

- یک Track به صفر یا یک PersonalRelationship

4.4 Track -> JournalEntry

از طریق JournalEntries.trackId.

- یک Track به چند JournalEntry

4.5 Track -> ListeningHistory

از طریق ListeningHistory.trackId.

- یک Track به چند رکورد ListeningHistory

4.6 روابطی که وجود ندارند

این روابط فعلاً واقعی نیستند:

- Artist -> Album در دیتابیس
- Artist -> Artist
- Track -> Work
- Work -> Version
- Track -> Credit
- Artist -> Role
- Album -> Official Track Order
- Track -> Source
- Track -> Artwork
- User -> Collection
- JournalEntry -> Work یا Artist
- ListeningEvent -> session/context/source

4.7 رابطهٔ مصنوعی در Graph

در seed.ts چند رابطهٔ Artist و Album به‌صورت constant تعریف شده‌اند و
Graph آن‌ها را با داده‌های SQLite ادغام می‌کند.

در نتیجه:

- این روابط داخل دیتابیس نیستند.
- backup آن‌ها را به‌عنوان relation مستقل ذخیره نمی‌کند.
- آلبوم‌های جدید کاربر نمی‌توانند به‌صورت واقعی به Artist متصل شوند.
- Graph با seed data coupling دارد.

4.8 Version فعلی

Version واقعی وجود ندارد.

در عوض:

- Trackهای دیگری با title یکسان پیدا می‌شوند.
- versionName فقط برای نمایش استفاده می‌شود.
- این رابطه بر اساس lower(trim(title)) ساخته می‌شود.

این روش ممکن است Trackهای کاملاً متفاوت را اشتباهاً version یکدیگر
نشان دهد.

5. GAPS AGAINST NAGHME 2.0
----------------------------------------------------------------------

PERSON

وجود ندارد.

Artists فعلاً به‌صورت هم‌زمان نقش شخص، هنرمند، گروه و performer را دارد.

ARTIST

به‌صورت محدود وجود دارد.

موجود:

- name
- biography
- genres
- images
- type

ناقص:

- نقش‌های متعدد
- نام‌های جایگزین
- منابع و شناسه‌های بیرونی
- روابط با هنرمندان دیگر
- تفکیک شخص و گروه

WORK

وجود ندارد.

عنوان موسیقی در Track ذخیره شده و composition از recording جدا نیست.

TRACK / RECORDING

وجود دارد، اما بیش از حد پرمسئولیت است.

Track فعلی هم‌زمان شامل metadata، audio asset، lyrics، sheet music،
album relation، artist relation و version label است.

VERSION

وجود ندارد.

versionName فقط یک string است و ساختار ندارد.

ROLE

وجود ندارد.

Artist.type جایگزین مناسبی برای role نیست.

CREDIT

وجود ندارد.

یک Track فقط یک artistId دارد و نمی‌تواند این ساختار را ذخیره کند:

- vocalist
- composer
- lyricist
- arranger
- musician
- conductor
- producer

SOURCE

وجود ندارد.

URIهای audio، sheet music و تصویر، provenance یا source محسوب نمی‌شوند.

ARTWORK

وجود ندارد.

تصویرها در چند ستون پراکنده ذخیره می‌شوند:

- Artists.image
- Artists.profileImage
- Artists.galleryImages
- Albums.coverImage
- Tracks.coverImage

RELATIONSHIP

به‌صورت محدود وجود دارد.

PersonalRelationships فقط رابطهٔ شخصی کاربر با Track را نگهداری می‌کند.

COLLECTION

وجود ندارد.

Album و Collection نباید یکی شوند:

- Album یعنی آلبوم منتشرشده یا canonical
- Collection یعنی گروه‌بندی شخصی کاربر

JOURNAL ENTRY

وجود دارد و بخش خوبی از هدف را پوشش می‌دهد.

نکتهٔ مثبت مهم این است که Journal آزاد است و چند entry برای یک Track را
پشتیبانی می‌کند.

LISTENING EVENT

به‌صورت ListeningHistory وجود دارد، اما فقط زمان شروع شنیدن را ذخیره
می‌کند.

6. PROPOSED DOMAIN MODEL
----------------------------------------------------------------------

پیشنهاد عملی، مرحله‌ای و سازگار با دیتابیس فعلی:

6.1 Artist / Person

در فاز اول نام Artists حفظ شود تا migration پرریسک نشود.

بعداً:

- Person: موجودیت انسانی یا گروه
- ArtistProfile: هویت هنری یا فعالیت موسیقایی شخص

فعلاً تفکیک کامل Person و Artist ضروری نیست.

6.2 Work

اثر موسیقایی مستقل از ضبط:

- id
- title
- alternateTitles
- description
- language
- genre
- notes
- createdAt
- updatedAt

هدف این است که چند ضبط یا نسخه بتوانند به یک اثر متصل شوند و عنوان اثر
با عنوان فایل یا ضبط یکی فرض نشود.

6.3 Track به‌عنوان Recording

برای جلوگیری از شکستن داده‌های فعلی، نام Tracks حفظ شود، اما از نظر
domain نقش آن یک آیتم قابل پخش یا recording در آرشیو شخصی باشد.

در آینده:

- Tracks.workId
- Tracks.versionId

اضافه شوند و فعلاً nullable باشند.

6.4 Version

Version برای توصیف تفاوت اجرایی یا تفسیری:

- studio
- live
- radio
- acoustic
- remastered
- cover
- alternate take
- سایر انواع

فیلدهای حداقلی:

- id
- workId
- name
- kind
- description
- notes
- createdAt
- updatedAt

در فاز اول Version نباید با حدس‌زدن title ساخته شود.

6.5 Role

جدول Role مستقل باشد، نه free-text در Artist.

نمونه roleها:

- vocalist
- composer
- lyricist
- arranger
- musician
- conductor
- producer
- ensemble
- other

Role باید قابل توسعه باشد و label فارسی/انگلیسی داشته باشد.

6.6 Credit

رابطهٔ چندبه‌چند بین Track، Artist و Role:

- trackId
- artistId
- roleId
- creditOrder
- note

این ساختار اجازه می‌دهد یک Track چند credit داشته باشد.

رابطهٔ فعلی Tracks.artistId باید برای سازگاری باقی بماند و بعدها به‌عنوان
legacy یا primary artist استفاده شود.

6.7 Album

Album باید از Collection جدا بماند.

فیلدهای پیشنهادی:

- title
- alternateTitles
- releaseYear
- releaseDate
- cover
- description
- genre
- label
- notes
- createdAt
- updatedAt

برای ترتیب قطعات، رابطهٔ جدا لازم است.

6.8 Album Track Order

برای ترتیب رسمی:

- albumId
- trackId
- discNumber
- trackNumber
- titleOverride
- notes

اگر یک Track بتواند در چند release یا album باشد، این مدل از
Tracks.albumId انعطاف‌پذیرتر است.

6.9 PersonalRelationship

در فاز اول همان رابطهٔ شخصی Track باقی بماند:

- rating
- favorite
- emotionalTags
- personalNote
- memories
- associations

listeningCount بهتر است در آینده از ListeningEvents محاسبه شود، نه اینکه
منبع مستقل حقیقت باشد.

6.10 JournalEntry

Journal باید همچنان free-form بماند.

فیلدهای آینده:

- trackId nullable یا فعلاً اجباری
- workId nullable
- note
- mood
- createdAt
- updatedAt

نباید Journal به فرم پرسش‌نامه‌ای تبدیل شود.

6.11 ListeningEvent

در مدل مفهومی جدید:

- id
- trackId
- startedAt
- endedAt
- listenedDuration
- completionPercent
- context
- source
- eventType

ListeningHistory فعلی می‌تواند تا پایان migration به‌عنوان legacy نگه
داشته شود.

6.12 Source

در فاز آینده:

- title
- URL
- sourceType
- author
- publicationDate
- notes
- createdAt

Source باید به entity مربوطه متصل شود، نه اینکه صرفاً داخل note نوشته شود.

6.13 Artwork

در فاز آینده یک entity مستقل:

- id
- uri
- artworkType
- title
- caption
- sourceId
- width
- height
- createdAt

سپس رابطهٔ جدا برای اتصال Artwork به Artist، Album، Track، Work و
Postcard Project ایجاد شود.

6.14 Collection

Collection باید کاملاً مستقل از Album باشد:

- id

8. MIGRATION STRATEGY
----------------------------------------------------------------------

دیتابیس نباید حذف و دوباره ساخته شود.

مرحلهٔ صفر: Backup محافظتی

قبل از هر migration:

1. export فعلی اجرا شود.
2. فایل backup نسخهٔ 1 حفظ شود.
3. تعداد رکوردهای هر جدول ثبت شود.
4. شناسه‌های موجود ثبت و immutable باقی بمانند.

مرحلهٔ یک: ایجاد migration واقعی

- معرفی schema versioning
- اجرای migrationها به‌ترتیب
- transaction برای هر migration
- شکست صریح در صورت خطا
- عدم swallow کردن خطاهای مهم
- verify کردن وجود جدول، ستون و foreign key

مرحلهٔ دو: Indexهای پایه

بدون تغییر domain:

- index روی Trackهای مرتبط با Artist و Album
- index روی JournalEntries.trackId و createdAt
- index روی ListeningHistory.trackId و listenedAt
- index روی titleهای قابل جست‌وجو

این مرحله کم‌ریسک‌ترین بهبود performance است.

مرحلهٔ سه: اصلاح listening count

یکی از دو سیاست باید انتخاب شود.

گزینهٔ پیشنهادی:

ListeningHistory/ListeningEvents تنها منبع حقیقت باشد و count با query
محاسبه شود.

مزیت:

- امکان اصلاح یا حذف event
- عدم ناسازگاری
- backup دقیق‌تر

گزینهٔ جایگزین:

اگر performance مهم باشد، listeningCount نگه داشته شود، اما:

- log listen و increment در یک transaction انجام شوند.
- حذف یا restore event نیز count را اصلاح کند.
- مقدار count دوره‌ای reconcile شود.

پیشنهاد اصلی گزینهٔ اول است مگر اینکه performance واقعی خلاف آن را نشان
دهد.

مرحلهٔ چهار: اضافه‌کردن Work و Version

- جدول Works ایجاد شود.
- Tracks فعلی حذف یا rename نشوند.
- workId و versionId ابتدا nullable باشند.
- برای هر Track فعلی یک mapping legacy ساخته شود.
- از deduplicate کردن خودکار بر اساس title خودداری شود.
- اگر title یکسان است، تا زمانی که کاربر یا منطق مطمئن تأیید نکرده،
  آن‌ها یکی فرض نشوند.

مرحلهٔ پنج: Credit و Role

- Roleهای پایه ایجاد شوند.
- از Tracks.artistId برای ساخت یک credit با نقش عمومی مثل primary artist
  استفاده شود.
- نباید از artistId فعلی نتیجه‌گیری شود که شخص حتماً خواننده یا آهنگساز
  بوده است.
- creditهای چندگانه فقط برای داده‌های جدید یا داده‌ای که کاربر تأیید
  کرده ساخته شوند.

مرحلهٔ شش: ترتیب Album

- جدول AlbumTracks اضافه شود.
- برای داده‌های فعلی که ترتیب رسمی ندارند، ترتیب موقت بر اساس ترتیب فعلی
  رکوردها ساخته شود.
- این ترتیب باید inferred تلقی شود، نه ترتیب رسمی تاریخی.
- اگر ترتیب واقعی در backup یا metadata موجود نیست، نباید آن را ادعا کرد.

مرحلهٔ هفت: ListeningEvent غنی‌تر

دو مسیر ممکن است:

1. اضافه‌کردن ستون‌های جدید به ListeningHistory
2. ساخت ListeningEvents جدید و انتقال داده‌های قدیمی

پیشنهاد:

- تا زمان تثبیت کد، ListeningHistory حفظ شود.
- سپس با migration مشخص به ListeningEvents منتقل شود.
- شناسه و timestamp قدیمی حفظ شوند.

مرحلهٔ هشت: به‌روزرسانی repository و domain types

پس از تثبیت schema:

- typeها از rowهای خام جدا شوند.
- query projectionها مدل مستقل داشته باشند.
- mapping مرکزی ایجاد شود.
- UI دیگر مستقیماً به aliasهای SQL وابسته نباشد.

مرحلهٔ نه: Backup نسخهٔ دو

Backup جدید باید:

- version مستقل داشته باشد.
- migration backup را پشتیبانی کند.
- تفاوت merge و replace را شفاف کند.
- نتیجهٔ واقعی Restore را اعلام کند.
- schema را با SELECT * وابسته نکند.
- media manifest و وضعیت URIها را مشخص کند.
- در صورت نیاز پروژه‌های Postcard Studio را نیز شامل شود.

10. RISKS
----------------------------------------------------------------------

10.1 از بین رفتن شناسه‌ها

شناسه‌های فعلی باید حفظ شوند.

تغییر ID باعث شکستن:

- روابط شخصی
- Journal
- History
- backupهای قدیمی
- لینک‌های داخلی routeها

10.2 تبدیل Track به Work

بزرگ‌ترین ریسک domain migration این است که Trackهای هم‌نام اشتباهاً یک
Work فرض شوند.

راه امن:

- ابتدا برای هر Track یک Work legacy بسازیم.
- ادغام Workها را به تصمیم بعدی یا تأیید کاربر موکول کنیم.

10.3 Artist واحد

از artistId فعلی نمی‌توان فهمید Artist:

- خواننده است
- آهنگساز است
- تنظیم‌کننده است
- گروه است
- یا فقط performer اصلی است

بنابراین migration نباید نقش دقیق را جعل کند.

10.4 Album order

ترتیب رسمی آلبوم فعلاً ذخیره نشده است.

مرتب‌سازی بر اساس title یا rowid، ترتیب رسمی تاریخی را ثابت نمی‌کند.

10.5 Listening count

وجود دو منبع count ممکن است باعث شود:

- recommendation اشتباه شود.
- Chat آمار متفاوتی نمایش دهد.
- صفحهٔ Track با recommendation ناسازگار باشد.

10.6 Restore

Restore فعلی:

- بر اساس ID upsert می‌کند.
- داده‌های غایب در backup را حذف نمی‌کند.
- بنابراین overwrite واقعی نیست.
- URIها و فایل‌های رسانه‌ای را جابه‌جا نمی‌کند.
- AI key و مدل را backup نمی‌کند.
- Postcard Studio projectها را backup نمی‌کند.

10.7 SELECT *

Backup به ترتیب ستون‌های فعلی وابسته است.

با اضافه‌شدن ستون یا تغییر schema، این روش می‌تواند shape نامطمئن تولید
کند.

10.8 URIهای محلی

audio، cover، profile و gallery به URIهای دستگاه وابسته‌اند.

انتقال backup به دستگاه دیگر ممکن است رکوردها را حفظ کند، اما فایل
رسانه‌ای دیگر وجود نداشته باشد.

10.9 AI و حریم خصوصی

Gemini context به Google ارسال می‌شود.

حتی اگر داده‌ها روی دستگاه ذخیره شوند، هنگام استفاده از AI دیگر کاملاً
local باقی نمی‌مانند.

همچنین کلید فعلی در AsyncStorage ذخیره می‌شود و secure storage نیست.

10.10 Web Preview

SQLite در web عمداً در دسترس نیست و database.web.ts مقدار null برمی‌گرداند.

بنابراین قابلیت‌های دیتابیسی در Web Preview قابل استفاده نیستند و این
رفتار باید در محصول و تست‌ها آگاهانه مدیریت شود.

10.11 Postcard Studio

Postcard Studio بسیاری از قابلیت‌های حرفه‌ای interaction را دارد، اما:

- پروژه‌ها ذخیره نمی‌شوند.
- فقط خروجی نهایی به Gallery می‌رود.
- در backup وارد نمی‌شود.
- position و scale عناصر persist نمی‌شوند.
- color wheel واقعی وجود ندارد.
- filterها عمدتاً overlay هستند، نه پردازش واقعی تصویر.
