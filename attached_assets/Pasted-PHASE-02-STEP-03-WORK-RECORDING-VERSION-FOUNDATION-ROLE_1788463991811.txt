--------------------------------------------------
3. CORE DOMAIN PROBLEM
--------------------------------------------------

The current Tracks table is overloaded.

A Track currently represents something similar to a recording, while also being used as the user's main musical item.

This is insufficient for a serious music archive.

We need to establish the following conceptual distinction:

WORK
The underlying musical/literary creation.

Examples:

- "بهار دلنشین"
- a specific classical composition
- a tasnif
- an instrumental composition

A Work is the composition/creation itself.

RECORDING
A particular recorded performance of a Work.

Example:

The same tasnif may have been recorded by different singers, in different years, with different orchestras or arrangements.

VERSION
A distinct version/arrangement/edit of a Work or Recording where this distinction is meaningful.

Examples may include:

- studio version
- live version
- alternate arrangement
- remastered version
- mono/stereo edition
- extended version

Do not assume that every Track must have a Version.

ALBUM
A release/container that contains one or more recordings.

TRACK
For this step, DO NOT attempt to completely rename or replace the existing Tracks table.

Treat the existing Track entity as the application's current recording-level item.

The architectural goal is to gradually evolve Track toward Recording without breaking the current application.

--------------------------------------------------
4. IMPORTANT DOMAIN RULES
--------------------------------------------------

These distinctions are critical:

Work != Recording

Recording != Album

Album != Work

Track != automatically Work

Track != automatically Album

A Work may have many Recordings.

A Recording may appear on multiple Albums.

An Album may contain multiple Recordings.

A Work may exist without any Recording.

A Recording may exist without being assigned to an Album.

An Album may exist without Tracks.

Do NOT assume that an album title represents a Work.

Do NOT assume that two tracks with the same title are the same Work.

Do NOT automatically merge records based on title.

Do NOT invent historical information.

Unknown relationships must remain unknown.

--------------------------------------------------
7. FOREIGN KEYS
--------------------------------------------------

Use proper foreign keys.

Tracks.workId -> Works.id
Tracks.versionId -> Versions.id
Versions.workId -> Works.id

Use safe delete behavior.

Do NOT allow deleting a Work to silently destroy existing Track data.

Prefer SET NULL behavior where appropriate for optional references.

Deleting a Work must not delete Tracks.

Deleting a Version must not delete Tracks.

Deleting a Work must not cascade into AlbumTracks.

--------------------------------------------------
8. VERSION RELATIONSHIP
--------------------------------------------------

A Version belongs to a Work.

Therefore:

Version.workId is required.

A Version cannot exist without a Work.

A Track may optionally reference:

- a Work
- a Version

If a Track references a Version, the Version must belong to the same Work referenced by the Track when both are present.

Do not create a complicated trigger system unless genuinely required.

If SQLite constraints cannot easily enforce this cross-reference, enforce it in the query/data-access layer and document the invariant.

11. WORK DATA MODEL
--------------------------------------------------

Work should be capable of representing a musical creation without requiring a recording.

Examples:

Work:
"بهار دلنشین"

Possible future recordings:

Recording/Track A:
performed by Singer A

Recording/Track B:
performed by Singer B

Recording/Track C:
live performance

The Work itself should not contain recording-specific fields such as:

- audioUri
- duration of a specific recording
- recording date
- specific album membership

Those belong to the recording/Track layer.
