==================================================
1. GOAL
==================================================

The current Naghme data model does not properly represent the different roles people can have in creating a musical work or recording.

For example, one musical item may involve:

- vocalist
- composer
- lyricist
- arranger
- musician
- conductor
- ensemble/group
- producer
- other contributor

The current single artist relationship is not sufficient.

The goal of this step is to introduce a flexible:

ROLE + CREDIT

model without destroying the existing Artist / Track relationships.

==================================================
2. IMPORTANT DOMAIN RULE
==================================================

Do NOT assume:

Artist = vocalist.

Do NOT assume:

Track.artistId = composer.

Do NOT assume:

Track.artistId = lyricist.

Do NOT infer credits from names, titles, albums, or existing seed data.

Existing artist relationships must remain intact.

New Credits should only be created when explicitly provided by existing structured data or through the new data model.

Unknown credits remain unknown.

==================================================
3. INSPECT FIRST
==================================================

Before editing, inspect the actual implementation of:

- Artists
- Tracks
- Albums
- AlbumTracks
- Works
- Versions
- Track.artistId
- all artist-related queries
- artist detail page
- track detail page
- album detail page
- graph queries
- seed data
- backup/restore
- integrity checker
- TypeScript models

Especially inspect how the current:

artistId

is being used.

Do not assume its meaning.

Determine whether it currently represents the primary artist, vocalist, creator, or simply the displayed artist.

Preserve its current behavior for compatibility.

==================================================
4. ROLE MODEL
==================================================

Create a flexible Roles model.

Suggested table:

Roles

Fields:

- id
- name
- key
- description

Examples:

- vocalist
- composer
- lyricist
- arranger
- musician
- conductor
- ensemble
- producer
- other

Do not hard-code the entire future taxonomy.

The model must allow additional roles later.

Use the project's existing ID and timestamp conventions where appropriate.

Do not create unnecessary fields.

==================================================
5. CREDIT MODEL
==================================================

Create a Credits table representing:

PERSON / ARTIST
+
ROLE
+
MUSICAL ENTITY

The credit should be capable of attaching an Artist to:

- Work
- Recording/Track
- Album

without creating three unrelated systems.

A practical model may contain:

- id
- artistId
- roleId
- workId nullable
- trackId nullable
- albumId nullable
- notes
- createdAt
- updatedAt

At least ONE target must be present:

workId
OR
trackId
OR
albumId

A single Credit must not point to multiple unrelated targets unless the model explicitly and safely supports that meaning.

Do not invent a polymorphic system that cannot be validated.

Prefer explicit nullable foreign keys if that fits the existing SQLite architecture.

==================================================
6. TARGET SEMANTICS
==================================================

Credits should support:

WORK CREDIT

Example:

Artist A
→ composer
→ Work X

TRACK / RECORDING CREDIT

Example:

Artist B
→ vocalist
→ Track X

Artist C
→ arranger
→ Track X

Artist D
→ musician
→ Track X

ALBUM CREDIT

Example:

Artist E
→ producer
→ Album X

These are different relationships.

Do not collapse them into a single artist field.

==================================================
7. WORK / TRACK RELATIONSHIP
==================================================

Use the Work / Version foundation created in Step 03.

Do not redesign Work, Version, Track, or AlbumTracks.

Credits should complement the existing model.

Do NOT create:

ComposerWork
LyricistWork
VocalistTrack
etc.

as separate tables.

Use the general Role + Credit model.

==================================================
8. ARTIST TYPES
==================================================

Inspect the current Artist model.

If it already supports types such as:

- person
- group
- ensemble

preserve the existing model.

Do not force all credits to represent individual people.

An ensemble/group should also be able to receive a valid Credit.

==================================================
9. LEGACY artistId
==================================================

DO NOT remove:

Tracks.artistId

Do NOT automatically convert it into a Credit.

Do NOT delete it.

Do NOT change its current behavior.

It remains for backward compatibility.

The new Credit system becomes the extensible source for explicit role-based relationships.

Do not duplicate the legacy artist relationship unless there is explicit data supporting that Credit.

==================================================

==================================================

Current database version after Step 03:

4

Create the next migration:

Migration 5

The migration must:

- create Roles
- create Credits
- create necessary indexes
- create foreign keys
- preserve all existing tables
- preserve all existing records
- preserve all IDs
- preserve Track.artistId
- preserve AlbumTracks
- preserve Works
- preserve Versions

- preserve JournalEntries

The migration must be:

- non-destructive
- transactional

- safe for existing databases

Do NOT fabricate Credits for existing Artists or Tracks.

Existing Credits should initially be empty unless explicit structured credit data already exists.

==================================================
11. FOREIGN KEYS
==================================================

Credits.artistId → Artists.id

Credits.roleId → Roles.id

Credits.workId → Works.id

Credits.trackId → Tracks.id

Credits.albumId → Albums.id

Optional target references should use safe behavior.

Deleting an Artist must not accidentally delete the Track itself.

Deleting a Role must not delete Artists, Tracks, Albums, or Works.

Deleting a Work must not delete Tracks.

Deleting an Album must not delete Tracks.

Follow the existing project's safe deletion conventions.

==================================================
12. VALIDATION
==================================================

Credit creation must validate:

- valid artistId
- valid roleId
- at least one target
- target exists
- target combination is valid

Examples:

VALID:

Artist + composer + Work

Artist + vocalist + Track

Artist + arranger + Track

Artist + producer + Album

INVALID:

Artist + role + no target

Artist + role + nonexistent Track

Artist + role + nonexistent Work

Artist + role + nonexistent Album

Do not silently create invalid credits.

==================================================
13. DUPLICATE CREDITS
==================================================

Prevent accidental duplicate credits.

For example:

Artist A
+ composer
+ Work X

should not be inserted twice accidentally.

Use an appropriate uniqueness strategy.

However, do not over-restrict legitimate situations.

If notes or future metadata make two identical-looking credits meaningfully different, document the decision.

Keep the model simple for this step.
